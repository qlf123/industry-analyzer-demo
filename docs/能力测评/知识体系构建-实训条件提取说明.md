## 1. 要解决的问题

能力测评需要知道「本校开设的课程需要哪些实训条件」。现在知识体系里没有这项信息，只能在知识体系建好之后另行推导、另行审核。

本文要求：**知识体系构建时，在生成技能规范及其下级内容之后，同步判定该技能需要的实训条件，作为技能规范的属性保存，随知识体系一起审核、发布、导出。** 能力测评直接读取已确认的结果。

### 不做的事

- 不在构建中生成任何数量（工位数、台套数、面积、每工位人数）。数量只来自标准原文，另行录入（维护规则 §3.4）。
- 不在构建中新建字典条目。字典由平台统一维护（维护规则 §3.1）。
- 不生成课程级实训条件。课程级只由人工维护（维护规则 §4）。
- 不把结果称为「标准要求」。页面与导出统一称「实训需求」。

## 2. 在构建流程中的位置

```
专业 → 课程分类 → 课程 → 任务 → 技能规范（可观察能力要求、达成结果）
                                     → 操作步骤 / 标准 / 案例 / 知识点
                                     → 【新增】实训条件判定（逐个技能）
专业（或本次范围）全部技能判定完成 → 【新增】专业级整合：实训条件清单 + 整合建议
                                     → 人工审核（与知识体系审核同一环节）
                                     → 发布
```

| 项 | 要求 |
|---|---|
| 触发时机 | 某技能规范的下级内容（操作步骤、标准、案例）生成完成后，对该技能规范执行一次判定 |
| 判定粒度 | 逐个技能规范判定；不跨技能合并 |
| 判定输入 | ① 该技能规范的完整路径（专业 › 课程分类 › 课程 › 任务 › 技能规范）；② 可观察能力要求、达成结果；③ 其下的操作步骤、标准、案例；④ 实训条件字典中「启用」的条目（编号、名称、类别、功能要点） |
| 判定规则 | 与推导规则 skill 一致：只能选字典条目；每个技能 0–3 项；分「必需 / 建议」；纯理论技能不输出；校外基地只在必须到真实场景时判必需；每条写依据 |
| 判定输出 | 每项：条件编号、级别、依据；以及 0–n 条「字典新增建议」（建议名称、类别、功能要点、触发它的技能） |
| 失败处理 | 判定失败不阻塞知识体系生成；该技能标「实训条件未生成」，可单独重试 |
| 已建成的知识体系 | 提供「补齐实训条件」操作，对指定专业 / 课程 / 技能批量执行同一判定，结果同样进入待审核 |

> 判定放在下级内容之后，是因为判定依据主要来自操作步骤与达成结果；只看技能名称容易误判（如名称含「模拟」「实训」并不代表必需实训室）。

## 3. 存储：技能规范节点的「实训条件」属性

### 3.1 字段

每条实训条件是挂在技能规范节点上的一条记录，字段沿用维护规则 §3.2（实训需求），构建环节需要写入的是：

| 字段 | 构建时取值 |
|---|---|
| 所属知识体系（专业） | 当前构建的知识体系 |
| 挂载类型 | 技能 |
| 挂载节点 ID | 技能规范节点 ID（**必须用 ID**，名称只作显示） |
| 条件编号 | AI 输出的字典编号 |
| 级别 | 必需 / 建议 |
| 依据 | 「技能侧：引用达成结果或步骤原文｜需要：为什么需要该条件」 |
| 来源 | auto |
| 状态 | 待审核 |
| 创建人 | 生成任务编号 |

### 3.2 校验（写入前）

| # | 规则 | 不通过时 |
|---|---|---|
| V1 | 条件编号必须是字典中「启用」的条目 | 丢弃该条，计入生成报告「无效编号」；若 AI 给的是名称而非编号，按名称精确匹配一次，仍匹配不到则转为「字典新增建议」 |
| V2 | 级别只能是必需 / 建议 | 丢弃该条 |
| V3 | 依据不能为空 | 丢弃该条 |
| V4 | 同一技能同一条件只保留一条；AI 重复输出时取较强级别 | 合并 |
| V5 | 单个技能超过 3 项 | 保留必需优先的前 3 项，其余计入生成报告「超出上限」 |
| V6 | 输出中出现数字型的数量描述（如「20 个工位」） | 依据中的数量文字原样保留（属于原文引用），但不得写入任何数量字段 |

### 3.3 重新生成

知识体系重新生成、或对已有知识体系执行「补齐实训条件」时，按维护规则 §6 合并：**AI 只改它自己生成、且仍为待审核的记录**；已审核、已调整、驳回的记录和全部人工记录都不动，驳回的不再出现。生成结束输出生成报告（新增、覆盖、删除、跳过、未再出现、字典新增建议、无效编号、超出上限各多少条）。

技能规范节点被删除时，其实训条件记录转为「失效」；节点恢复时回到失效前的状态（维护规则 §5.1）。

## 4. 构建完成后的整合

逐个技能判定时，多个技能会引用同一项实训条件（如十几个技能都需要「导游服务综合实训室」）。记录本身不重复（引用的是同一字典编号），但需要在专业层面整合一次：给出专业级清单，并找出逐技能判定看不到的问题。

### 4.1 触发

| 项 | 要求 |
|---|---|
| 自动触发 | 一个专业（或「补齐实训条件」的指定范围）内全部技能判定完成后执行一次 |
| 手动触发 | 审核过程中可随时「重新整合」，用于刷新清单与建议 |
| 范围 | 整个专业；指定课程补齐时，清单仍按整个专业重算，建议只针对本次范围 |

### 4.2 产出一：专业实训条件清单

按条件汇总全专业的有效记录（待审核、已审核、已调整），每项一行：

| 列 | 口径 |
|---|---|
| 实训条件 | 名称、类别、功能要点 |
| 级别 | 任一技能或课程级记录为必需 → 必需；否则建议 |
| 需要它的课程 | 按级别分列：必需该条件的课程、只是建议的课程 |
| 技能数 | 引用该条件的技能个数（必需 / 建议分别计） |
| 审核进度 | 已确认 n 条、待审核 m 条 |

- 清单是**由记录汇总出来的视图**，不能直接编辑；要改，回到具体技能或课程的记录上改。
- 清单随知识体系版本保存一份，供对比不同版本间的变化。
- 能力测评第 ② 步的「标准要求的实训条件」，就是这份清单在**本校已开设课程范围内、只计已确认记录**的结果。

### 4.3 产出二：整合建议

整合只**提出建议**，进入审核列表，由审核人逐条采纳或忽略；**不自动改动任何记录**。采纳后的改动按维护规则 §5.1 的状态流转执行（如改级别 → 已调整，驳回 → 驳回）。

| 建议类型 | 触发 | 建议内容 | 采纳后 |
|---|---|---|---|
| 级别不一致 | 同一任务下的多个技能引用同一条件，有的必需、有的建议 | 列出这些技能与各自依据，提示统一级别 | 审核人逐条修改级别（→ 已调整） |
| 上提为课程级 | 一门课中引用同一条件的技能数达到该课技能总数的设定比例（平台配置，见第 10 节） | 建议在该课程上挂一条课程级记录 | 由审核人人工创建课程级记录；技能级记录保留，两条并存（维护规则 §4） |
| 可由一项覆盖 | 同一课程内两项条件总是在同一批技能上同时出现，且由 AI 依据两者的功能要点判断其中一项可以覆盖另一项（如综合实训室覆盖单项场景） | 列出两项条件、涉及技能与覆盖理由，建议保留覆盖范围大的一项 | 审核人驳回被覆盖项（理由「由 X 覆盖」），保留另一项 |
| 孤例复核 | 某条件在全专业只被 1 个技能引用，且为必需 | 提示复核该判定是否成立 | 审核人通过、修改或驳回 |
| 字典新增建议合并 | 多个技能提出名称或功能相近的字典新增建议 | 合并为一条，附全部触发技能 | 进入字典「待处理建议」（第 5 节） |

### 4.4 生成报告

整合结束在生成报告中追加：清单条件数（必需 / 建议）、各类整合建议的条数。

## 5. 审核

| 项 | 要求 |
|---|---|
| 审核入口 | 知识体系审核页面中，技能规范节点详情增加「实训条件」区块，与「可观察能力要求」「达成结果」同屏 |
| 每条显示 | 条件名称（及类别）、级别、依据、来源（AI / 人工）、状态 |
| 操作 | 通过、修改后通过（改条件或级别）、驳回（必填理由）、恢复；人工新增（直接为已审核）；状态流转见维护规则 §5.1 |
| 批量 | 支持按课程、按条件批量通过；不支持批量修改级别 |
| 知识体系整体发布 | 不要求实训条件全部审核完成；未审核的记录随知识体系发布，但**能力测评只计入已审核、已调整的记录** |
| 整合建议 | 审核页增加「专业实训条件」视图：上方为专业清单，下方为整合建议列表，可逐条采纳或忽略；忽略的建议在重新整合时不再提示（除非涉及的记录发生变化） |
| 字典新增建议 | 汇总到字典管理的「待处理建议」列表（已按第 4.3 节合并），由平台数据管理员决定新增、合并到已有条目或忽略；新增后可对相关技能重新执行判定 |

## 6. 导入导出

沿用知识体系现有的 Excel 格式，**在「节点属性数据」表中按属性行写入**，不新增工作表。技能规范节点已用同一方式存放「可观察能力要求」「达成结果」。

| 列 | 写法 |
|---|---|
| 体系路径 | 技能规范的完整路径（只在该节点第一行填写，后续属性行留空，与现有规则一致） |
| 属性名称 | `实训条件` |
| 属性值 | `条件编号:级别`，如 `LAB-GUIDE:必需` |
| 属性描述 | 依据；导出时在依据末尾附 `［来源/状态］`，如 `［auto/已审核］` |

示例（同一技能需要两项条件，写两行）：

| 体系路径 | 节点描述 | 节点层级信息 | 属性名称 | 属性值 | 属性描述 |
|---|---|---|---|---|---|
| 导游（540102）--专业核心课程--模拟导游--…--接待计划编制与确认 | … | 类型:技能规范 | 实训条件 | LAB-GUIDE:必需 | 技能侧：…完成接待演练｜需要：模拟带团场景［auto/已审核］ |
| | | | 实训条件 | EQ-DOC:必需 | 技能侧：研读接待任务书、编制行程单｜需要：单据样本［auto/已审核］ |

**导出**：默认导出全部有效记录（待审核、已审核、已调整），可选「只导出已确认」；驳回、失效的不导出。

**导入**：

| 情况 | 处理 |
|---|---|
| 属性值格式不是 `编号:级别` | 该行报错，其余行照常导入 |
| 编号不在字典中或已停用 | 该行报错 |
| 属性描述（依据）为空 | 该行报错 |
| 属性描述中带有［来源/状态］ | 按其恢复来源与状态；不带时视为人工维护（manual / 已审核） |
| 与库中同一技能同一条件已有记录 | 按维护规则 §6 合并（导入视为一次「生成」，但导入的人工记录覆盖同条件的 auto 待审核记录） |

## 7. 与能力测评的衔接

- 能力测评读取各专业知识体系中**已审核、已调整**的实训条件记录，按维护规则 §7 汇总到课程、能力 × 等级，再与本校填报的实训资源对照（维护规则 §8）。
- 能力测评第 ② 步「实训资源」列出的标准清单，即来自这里：本校已开设课程下全部技能的已确认实训条件，按条件汇总，必需在前。
- 某专业尚无任何已确认的实训条件时，能力测评的实训部分显示「本专业暂无已确认的实训需求，本次不作实训条件对比」。

| 专业 | 做法 |

## 9. 验收用例

| # | 场景 | 预期 |
|---|---|---|
| A1 | 构建一个新专业，某技能达成结果为「在模拟车厢完成站位讲解」 | 生成「导游服务综合实训室」或对应条件、级别必需、依据引用该达成结果；状态待审核，来源 auto |
| A2 | 某技能为纯概念辨析（如「旅游概念界定与辨析能力」） | 不生成实训条件 |
| A3 | AI 输出了字典中不存在的「VR 眼镜」 | 不写入实训条件；在字典「待处理建议」中出现一条，含触发它的技能 |
| A4 | AI 输出编号已停用的条件 | 不写入；生成报告「无效编号」+1 |
| A5 | 某技能 AI 输出 5 项条件 | 只保留 3 项（必需优先）；生成报告「超出上限」+2 |
| A6 | 实训条件判定接口失败 | 知识体系其余内容正常生成；该技能标「实训条件未生成」，可单独重试 |
| A7 | 专家把某条从必需改为建议后，重新构建该课程 | 该条保持「已调整 / 建议」，不被覆盖 |
| A8 | 专家驳回某条后，重新构建 | 该条不再出现 |
| A9 | 导出知识体系，选「只导出已确认」 | 只有已审核、已调整的实训条件属性行；属性值为 `编号:级别`，描述带［来源/状态］ |
| A10 | 导入时某行属性值写成「导游服务综合实训室:必需」 | 该行报错「编号不在字典中」，其余行导入成功 |
| A11 | 知识体系发布时仍有待审核的实训条件 | 允许发布；能力测评中这些记录不计入，第 ② 步「生成报告」旁提示「有待确认的数据，本次不计入」 |
| A12 | 删除一个已有实训条件的技能规范节点 | 其实训条件记录转为失效，不再出现在课程汇总与能力测评中 |
| B1 | 全专业 12 个技能引用「导游服务综合实训室」，其中 3 个必需 | 专业清单中该条件只出现一行：级别必需，必需课程与建议课程分列，技能数 3 / 9 |
| B2 | 同一任务下两个技能对「急救技能训练器材」一个判必需、一个判建议 | 出现一条「级别不一致」建议；不采纳时两条记录保持原样 |
| B3 | 《模拟导游》中达到设定比例的技能都需要「导游服务综合实训室」 | 出现「上提为课程级」建议；采纳后新增一条人工课程级记录，技能级记录不变 |
| B4 | 同一课程内「讲解实训室」与「导游服务综合实训室」总在同一批技能上同时出现 | 出现「可由一项覆盖」建议并附理由；审核人驳回其一后，专业清单只剩另一项 |
| B5 | 整合运行后不做任何审核操作 | 所有实训条件记录的状态、级别与整合前完全一致 |
| B6 | 审核人忽略某条建议后点「重新整合」 | 该建议不再出现；若涉及的记录后来被修改，再次整合时重新出现 |

## 10. 待确认

| # | 问题 | 建议 |
|---|---|---|
| 1 | 每个技能的条件上限是否固定为 3 项 | 先按 3 项，生成报告里观察「超出上限」的频率再调整 |
| 2 | 判定是否使用与知识体系构建相同的模型 | 建议相同；判定提示词以推导规则 skill 的 RULES 段为准，规则调整只改 skill |
| 3 | 审核权限是否沿用知识体系审核专家 | 建议沿用（维护规则 §5.2） |
| 4 | 「上提为课程级」的比例 | 平台可配置，建议先设为该课技能数的一半以上，按实际采纳率再调 |
| 5 | 「可由一项覆盖」是否需要 AI 判断 | 建议需要：只凭共现会误报（两项条件同时需要也很常见），由 AI 依据功能要点判断能否覆盖，结论仍由人审 |

## 11. 对「自动构建专业知识体系流程」的改动

> 对象：Dify 工作流「自动构建专业知识体系流程」（223 自动构建体系工作流，DSL 0.6.0）。以下按节点标题指代节点。
> 现状要点：每个任务按课程类型走 5 条分支之一——「LLM-xx类任务拆解 → Code-xx类清洗 → HTTP-xx类入库（`/knowledge/course/build-from-skills`）」；技能规范已带 `tools_materials_equipment_conditions`（工具材料设备）与 `extended_attributes`（扩展属性，入库后即节点属性，对应导出表的「属性名称 / 属性值 / 属性描述」）；只有实操技能类要求生成「训练环境」扩展属性，理论认知类、职业素养类的工具材料设备字段固定为 null。

### 11.1 改动总览

| # | 位置 | 类型 | 改动 | 目的 |
|---|---|---|---|---|
| W1 | 「Code 知识体系三层结构解析」之后、「迭代-课程任务框架生成」之前 | 新增节点 | **HTTP-获取实训条件字典**：读取启用的字典条目（编号、名称、类别、功能要点） | 字典只取一次，传入后续迭代 |
| W2 | 「LLM-岗位应用类 / 职业素养类 / 综合拓展类任务拆解」 | 修改提示词 | 技能规范的必含扩展属性增加「训练环境」；职业素养类的工具材料设备字段改为按需填写（见 11.2） | 给判定提供直接依据；实操技能类已有，理论认知类不改 |
| W3 | 「迭代-单任务深度拆解与入库」内，5 个「Code-xx类清洗」之后 | 新增节点 | **变量聚合器-拆解结果** → **LLM-实训条件判定** → **Code-实训条件校验与合并** | 判定本任务每个技能的实训条件，写入技能规范扩展属性（11.3、11.4） |
| W4 | 5 个「HTTP-xx类入库」 | 修改 | 合并为一个 **HTTP-任务入库**：数据取「Code-实训条件校验与合并」的输出，`course_type` 取「Code-解析任务项」的课程类型 | 判定接在 5 条分支汇合之后，避免在每条分支各加一套节点 |
| W5 | 「LLM-实训条件判定」失败分支 | 新增节点 | **Code-实训条件判定容错**：不加实训条件，原样入库，并在技能扩展属性中写「实训条件：未生成」 | 判定失败不阻塞知识体系入库（第 2 节） |
| W6 | 「Code-单任务入库结果收集」 | 修改代码 | 结果中增加本任务的实训条件判定结果、校验丢弃明细、字典新增建议 | 供迭代结束后整合使用 |
| W7 | 「迭代-单任务深度拆解与入库」之后、「Code-构建结果汇总」之前 | 新增节点 | **Code-实训条件专业汇总** → **LLM-可覆盖判断** → **Code-整合建议生成** → **HTTP-实训条件整合结果入库** | 第 4 节：专业清单与整合建议 |
| W8 | 「Code-构建结果汇总」 | 修改代码 | 执行报告追加实训条件统计（第 3.3、4.4 节的各项条数） | 生成报告 |
| W9 | 平台接口 | 新增 / 修改 | 见 11.6 | — |
| W10 | 新工作流 | 新增 | **补齐实训条件**：对已建成的知识体系按专业 / 课程 / 技能范围执行判定与整合 | 第 2、8 节 |

改动后单个任务的路径：

```
Code-解析任务项 → 条件分支-课程类型分发 → LLM-xx类任务拆解 → Code-xx类清洗
  → 变量聚合器-拆解结果 → LLM-实训条件判定 → Code-实训条件校验与合并 → HTTP-任务入库 → Code-单任务入库结果收集
                              └（失败）→ Code-实训条件判定容错 ┘
```

### 11.2 修改提示词：任务拆解（W2）

**岗位应用类、综合拓展类**：在「节点扩展属性规则」中，技能规范的必含项增加「训练环境」，并加一条写法要求：

```
- 技能规范必含（新增）：训练环境——写明完成该技能所需的场所类型（普通教室 / 机房 / 实训室名称 / 模拟场景 / 校外真实岗位）及关键设施、设备、软件、单据；普通教室即可完成的，写「普通教室」。
```

**职业素养类**：同上增加「训练环境」；输出格式中的 `"tools_materials_equipment_conditions": null` 改为：

```
"tools_materials_equipment_conditions": "训练所需设施或用品（如形体镜、化妆镜台、服装道具）；无则填 null",
```

**实操技能类**：已有「训练环境」，在其写法上补同一句要求（场所类型 + 关键设施，普通教室写「普通教室」）。

**理论认知类**：不改。

> 只增加属性、不改变原有节点结构与字数要求；改完后用 2～3 个已建专业的课程回归，确认拆解质量与入库不受影响。

### 11.3 新增：LLM-实训条件判定（W3）

| 项 | 设置 |
|---|---|
| 模型 | 与任务拆解相同（当前 qwen3.6-plus）；温度取低值，保证同一输入结果稳定 |
| 输入 | 实训条件字典（W1 的输出）、课程名称、课程类型、本任务清洗后的拆解结果（JSON） |
| 输出 | JSON，见下 |
| 失败 | 走失败分支到「Code-实训条件判定容错」 |

提示词（判定规则正文以 `.claude/skills/training-condition-derivation/SKILL.md` 的 RULES 段为准，规则调整时同步替换下文「判定规则」部分）：

```
# 角色
你是职业院校实训教学条件分析员。根据任务拆解结果，判断每个技能规范在教学与考核时需要哪些实训条件。

# 输入
【实训条件字典】{{实训条件字典}}   ← 只能从中选择，按编号引用
【课程】{{课程名称}}（{{课程类型}}）
【任务拆解结果】{{本任务清洗后的 JSON}}

# 判定规则
1. 逐个技能规范判断，依据为：达成结果（achievement_result）、操作步骤（operation_steps 的 step_content 与 completion_result）、工具材料设备（tools_materials_equipment_conditions）、扩展属性中的「训练环境」，以及标准与案例。不得只凭技能名称或课程名称判断（名称含「模拟」「实训」不代表必需）。
2. 级别：
   - 必需：离开该条件，达成结果或操作步骤中的动作无法完成或无法考核；
   - 建议：有该条件教学效果明显更好，但普通教室或纸面也能完成；
   - 纯理论、概念辨析、方案撰写等普通多媒体教室即可完成的技能，不输出任何条件。
3. 每个技能 0～3 项；能由一项综合实训室覆盖的，不拆成多个设备。
4. 校外基地只在必须到真实场景时判必需（如实地资源调查、跟团带团）；能在校内模拟的判建议。
5. 只能引用字典中的编号；字典里没有合适条目时，不要编造编号，写入 dictionary_suggestions。
6. 不输出任何数量（工位数、台套数、面积、人数）。
7. 依据写成「技能侧：引用达成结果或步骤原文｜需要：为什么需要该条件」。

# 输出 JSON（只输出 JSON）
{
  "skills": [
    {
      "skill_spec_name": "与输入中的技能规范名称完全一致",
      "conditions": [
        { "condition_id": "字典编号", "level": "必需 或 建议", "basis": "技能侧：……｜需要：……" }
      ]
    }
  ],
  "dictionary_suggestions": [
    { "name": "建议新增的条件名称", "category": "场地/场景/设备耗材/软件/校外基地", "spec": "功能要点", "skill_spec_name": "触发它的技能规范" }
  ]
}
```

### 11.4 新增：Code-实训条件校验与合并（W3）

| 步骤 | 行为 |
|---|---|
| 1. 解析 | 解析判定输出（容忍 ```json 包裹，与现有清洗节点同一做法） |
| 2. 匹配技能 | 按 `skill_spec_name` 匹配拆解结果中的技能规范；匹配不到的判定结果丢弃，计入「无法匹配技能」 |
| 3. 校验 | 按第 3.2 节 V1～V6 执行：编号须在字典中且启用（给了名称的按名称精确匹配一次，仍不中的转为字典新增建议）；级别只能必需 / 建议；依据不能为空；同一技能同一条件去重取较强级别；超过 3 项保留必需优先的前 3 项 |
| 4. 写入 | 每条通过校验的结果，追加到对应技能规范的 `extended_attributes`：`attribute_name` = 「实训条件」，`attribute_value` = 「编号:级别」，`attribute_description` = 依据 + 「［auto/待审核］」 |
| 5. 输出 | 合并后的任务 JSON（交给 HTTP-任务入库）；校验丢弃明细与字典新增建议（交给 Code-单任务入库结果收集） |

### 11.5 新增：迭代结束后的整合（W7）

| 节点 | 行为 |
|---|---|
| Code-实训条件专业汇总 | 汇总全部任务的实训条件结果，按第 4.2 节生成专业清单；按第 4.3 节找出「级别不一致」「上提为课程级」「孤例复核」三类建议；把相似的字典新增建议合并；找出同一课程内总是同时出现的条件对，作为「可由一项覆盖」的候选 |
| LLM-可覆盖判断 | 只对候选条件对调用：输入两项条件的名称与功能要点、共同涉及的技能及依据，输出「能否由其中一项覆盖」及理由；无候选时跳过 |
| Code-整合建议生成 | 合并上述结果为整合建议列表，每条含类型、涉及条件与技能、理由 |
| HTTP-实训条件整合结果入库 | 写入专业清单快照（随知识体系版本）与整合建议（进入审核列表）；字典新增建议写入字典「待处理建议」 |

LLM-可覆盖判断提示词要点：

```
判断条件 A 能否覆盖条件 B：只有当 A 的功能要点能完整支持 B 所涉及技能的全部动作时，才判「可覆盖」；
两项条件只是常一起使用、但各自承担不同功能的，判「不可覆盖」。
输出 JSON：{ "coverable": true/false, "keep": "保留的条件编号", "reason": "理由" }
```

### 11.6 接口改动（W9）

| 接口 | 类型 | 说明 |
|---|---|---|
| 获取启用的实训条件字典 | 新增 | 供 W1 调用：返回编号、名称、类别、功能要点 |
| `/knowledge/course/build-from-skills`（任务入库） | 修改 | 识别属性名称为「实训条件」的扩展属性，按维护规则 §3.2 存为实训需求记录（挂载节点 = 新建的技能规范节点 ID，来源、状态取描述末尾的［auto/待审核］），同时作为节点属性保留以便导出；编号不在字典中的拒收该条并在响应中返回 |
| 实训条件整合结果入库 | 新增 | 供 W7 调用：写入专业清单快照、整合建议、字典新增建议 |
| 技能节点实训条件写入（补齐用） | 新增 | 供 W10 调用：对已有技能节点写入判定结果，按第 3.3 节（维护规则 §6）合并，返回新增 / 覆盖 / 跳过 / 未再出现的条数 |
| 按专业读取技能规范及下级内容 | 新增或复用 | 供 W10 调用：返回技能规范的达成结果、操作步骤、工具材料设备、训练环境、标准、案例 |

### 11.7 新增工作流：补齐实训条件（W10）

```
输入（专业 system_id，可选课程 / 技能范围）
→ HTTP-获取实训条件字典 → HTTP-按专业读取技能规范 → 迭代（按任务）：LLM-实训条件判定 → Code-实训条件校验与合并 → HTTP-技能节点实训条件写入
→ 迭代结束：与 W7 相同的整合节点 → 执行报告
```

判定提示词、校验规则与构建流程共用，保证新建专业与已建专业的结果口径一致。导游（540102）可先导入已有推导草稿（第 8 节），再用本工作流对未覆盖的技能补齐。

### 11.8 影响

| 项 | 影响 |
|---|---|
| 调用量 | 每个任务多 1 次模型调用；整合阶段按候选条件对调用，通常为个位数到几十次 |
| 耗时 | 「迭代-单任务深度拆解与入库」现为 10 路并行，判定节点在迭代内，按任务数线性增加；判定输入只含本任务内容，长度明显小于拆解输出 |
| 失败 | 判定失败走 W5 容错，知识体系照常入库；执行报告列出「实训条件未生成」的任务，可用 W10 单独补齐 |
| 回归 | W2 改了 3 类拆解提示词，须回归验证原有节点与入库；W4 合并入库节点后，须验证 5 类课程均能正常入库 |
