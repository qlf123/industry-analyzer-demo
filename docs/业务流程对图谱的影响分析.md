# 业务流程对图谱的影响分析

> 2026-11-12 · 目标：回答「全部数据入图（全景图谱）」前，先讲清**目前每个业务流程对图谱产生什么影响**，以及**版本和子图如何承接这些影响**。对照《岗课赛证一体化平台·全链路数据图谱设计》v1.0（2026-10-22，52 实体 / 43 关系 / 5 链路）。

---

## 一、全景图谱的入图口径（现状规则，pano-version.js 头注）

先固定四条规则，后面所有流程的影响都按这四条归类：

| # | 规则 | 原型实现 |
|---|---|---|
| R1 | **全景图谱不自建主体节点**，只合并 4 个来源：能力图谱（行业级）· 知识体系（专业级）· 标准库·赛项 · 标准库·证书 | `SOURCES[ag/ks/comp/cert]`，另有 `self`（老师个人补充） |
| R2 | **骨架进版本，资源不进版本**：来源节点 + 跨来源关系随版本发布；知识库资料/教学资源实时挂载在节点上 | 同步→草稿→人工发布；已发布只读；同一专业单草稿 |
| R3 | **发布单元是专业**：行业视图、「全部」大图谱只汇总不发布 | `MAJORS` 映射；「全部」= 各专业当前已发布版本合集 |
| R4 | **回滚只切当前版本，不回退来源图谱** | manifest 记录本次版本引用的各来源版本号 |

子图（pano-subgraph.js）三条规则：**只存规则不存数据**（起点+链路+筛选，打开时实时取数）；**可见范围 = 子图范围 ∩ 数据权限**；**默认跟随最新已发布版本，可锁定在保存时的版本**。场景子图模板 4 个：课程图谱（已就绪）、岗位能力图谱 / 备赛图谱 / 考证图谱（`ready:false`，等待对应数据入图后开放）。

## 二、业务流程 → 图谱影响矩阵（核心）

图例：**版本影响** = 是否产生草稿/需要发布；**子图影响** = 对子图取数范围/场景模板的影响。

### 2.1 图谱供给侧（改图谱本身的流程）

| 业务流程 | 数据影响 | 来源层 | 版本影响 | 子图影响 |
|---|---|---|---|---|
| ① 图谱中心 · 能力图谱建模/修订（Python 构建链或图谱中心页） | 新增/修改/停用 **岗位、能力点、能力→技能映射**；版本号 v1.x 递增 | ag | 来源自身发版 → 全景**感知到新版本**，出现「可同步」角标；同步后进**全景草稿**，人工发布生效 | 「岗位能力图谱」场景模板的解锁条件；能力项/岗位节点进入所有子图的可选范围 |
| ② 图谱中心 · 知识体系建模（含 AI 生成，接 Dify 入口） | 课程 › 任务 › 技能 › 知识点（name/type/core）；版本 v2.x | ks | 同上，同步进草稿 → 发布 | 「课程图谱」场景子图的数据源；知识点是学情/补训的锚 |
| ③ 图谱中心 · 课程关联知识体系（教务在课程管理补选/接管/解除） | **课程节点与知识体系的挂接关系变化**（一对一/一对多、GKS- 课程知识体系） | ks | 不改图谱节点本身；但**改变课程→技能→知识点的可达路径** → 影响下次同步的映射缺口统计 | 「课程图谱」子图两跳范围（课程→章节/知识点→技能，不越过其他课程）随之变化 |
| ④ 图谱建议审核（老师提交 → 采纳/退回 → 发布并入标准图谱） | 采纳后**并入标准图谱（ag）下个版本**，署名教研贡献；退回重提不产生版本 | ag → self | 双跳版本：先 ag 发版，再**全景同步→草稿→发布**才对全专业可见 | 已发布后节点在所有子图可见；审核中的建议**不出现**在任何子图（权限=已发布版本） |
| ⑤ 老师能力地图 · 我的补充（个人节点） | 个人节点**实时显示**在能力地图（self 源，`sourceVer: '—'`），标注「随全景版本发布」 | self | 个人补充**实时可见但不属于任何已发布版本**；经④采纳发布后才固化 | 原型中个人节点不进子图（未发布）；规划口径：未发布建议只对作者可见 |

### 2.2 教学侧（不改图谱，但依赖图谱的流程）

| 业务流程 | 数据影响 | 来源层 | 版本影响 | 子图影响 |
|---|---|---|---|---|
| ⑥ 教务 · 排课（course-plan） | **零**：排课是时序事实，不产生任何图谱数据 | — | 无 | 无 |
| ⑦ 备课（workbench）：资源包生成、能力地图带入 | **资源挂载**：备课资源包记下 skillIds（来自图谱技能），资源可挂载到节点展示层 | 展示层 | **不随版本**（R2）——资源实时挂载，图谱回滚后资源仍在 | 「找资源」检索、节点资源角标（res-badge）；资源悬挂提示（来源节点停用时挂载资源不自动删除，只标悬挂） |
| ⑧ 发布任务（teacher-tasks publish） | **快照事务**：`task.skillIds + kpIds + kpSnap`（知识点名称/类型/核心内容）随任务固化；之后图谱改了不影响已发布任务 | 事务侧 | 无（发布的是任务，不是图谱版本） | 原型未做；规划口径为 `ASSEMBLED_FROM`（任务由能力点组装），若入图则新增任务节点层 |
| ⑨ 评价确认 / 学情（达成、掌握度） | **零图谱写入**：技能达成=最近一次通过证据、知识点掌握=最近一次老师确认评价，全部是时序事实 | 事务侧 | 无 | 无。规划原文警示：**掌握度放进图库是最易犯的错**——它是时序事实不是结构，图库只放当前值快照 |
| ⑩ 学情缺口 → 发起补训 | 补训课次带 `targets`（未掌握知识点/技能），回到⑦⑧再教再考；**不改图谱** | 事务侧 | 无 | 规划口径：缺口作为 `GAPS_ON` 回流入图（资源缺口→能力点），驱动补资源决策 |
| ⑪ 全景同步/发布/回滚（专业负责人操作） | 影响分析（节点停用→关系失效、等级变化→待复核、改名→保留）→ 合并进草稿 → 两级校验（覆盖率阈值/孤立节点/能力点无知识点**阻止发布**）→ 发布生成新版本 + manifest | 全部来源 | **版本中枢**：本流程是所有供给侧流程（①②④）变更对全专业生效的唯一通道 | 各专业当前版本 = 子图默认取数基准；「全部」大图谱 = 各专业当前版本合集 |
| ⑫ 子图保存/分享（pano-subgraph） | **零**：只存规则；可锁版本（`lock`），来源图谱升级后提示「已不在锁定版本」 | — | 锁定版本与当前版本不一致时给出 diff 提示 | 子图本身 |

### 2.3 一句话总结矩阵

> **改图谱的流程只有 5 个（①②③④⑤），它们全部经由 ⑪「同步→草稿→发布」才对全专业可见；教学侧流程（⑥–⑩）不写图谱结构，只通过资源挂载（⑦）和将来可能的任务/掌握度快照与图发生关系。子图永远是只读消费者，靠「实时取数 + 版本锁定」跟上图谱变化，不需要任何同步动作。**

## 三、对照整体规划 v1.0：已对齐 / 待补齐

### 3.1 原型已对齐规划的点

| 规划要求 | 原型现状 |
|---|---|
| GraphVersion「发布即快照，只读」+ manifest 记来源版本 | ✓ 版本记录含 manifest（各来源版本号）、变更摘要（nodeAdd/nodeOff/relAdd/relOff/review）、操作人 |
| ImpactRecord「图谱变更前必查」影响分析 | ✓ 同步时自动列节点停用/等级变化/改名，标注受影响关系与悬挂资源 |
| 掌握度不入图库（时序事实） | ✓ 评价/达成/掌握全在事务侧（localStorage），图库零掌握度数据 |
| 资源不进版本、实时挂载 | ✓ 「资源不是图谱节点，只作为展示层叠加」（resBtn title 原话） |
| 发布前校验（覆盖率/孤立节点） | ✓ 两级校验，且「能力点无知识点」阻止发布——与规划六条自检清单同思路 |
| 子图 SNAPSHOT_OF / 版本锁定 | ✓ 子图可锁版本，版本漂移有提示 |
| 按专业隔离 | ✓ 发布单元=专业，权限子图按专业过滤 |

### 3.2 「全部数据入图」前必须补齐的差距

按影响从大到小：

1. **标准库（赛项/证书）是 mock**：只有 2 个演示节点（comp/cert 各一）+ 少量考核要求。备赛图谱/考证图谱/岗位能力图谱三个场景子图全部 `ready:false`。**这是「全部入图」最大的一块空白**——赛项评分点、证书考点需要像能力↔技能映射一样，先做结构化映射数据（对应规划 `MAPS_TO`：证/赛 → 能力点/知识点）。
2. **备课资源没有真实挂载到节点**：原型挂载的是 mock 知识库资料/教学资源；真实的备课资源包（`resIds`）记了 skillIds 但没有回挂到图谱节点。规划要求「每个 Resource 挂至少 1 个 Ability」（自检清单第 6 条）。需要打通：资源包生成时按 skillIds → 映射到能力项 → 写挂载关系。
3. **任务层未入图**：发布任务/考查技能/证据链没有图谱表达（规划 `ASSEMBLED_FROM`、`EVIDENCE_FOR`、五类证据）。建议先做成**展示层叠加**（同资源模式）而非图节点，避免图库时序化。
4. **掌握度快照未上图**：规划允许 Neo4j 放「当前值快照」供路径查询（PG 为准，异步同步）。原型完全没做——学生在图谱上看不到「这个能力点我的掌握情况」。入图方式：只放当前值，评价发生时更新快照。
5. **知识体系五种关系缺失**：规划知识点间只有 `PRE_REQUIRES / CONTAINS / PARALLEL / CONFUSES_WITH / SAFETY_CONSTRAINT` 五种关系，各自驱动学习路径、错题溯源、**实操准入硬门禁**（"这条规则要写进任务发布接口"）。原型知识点只有层级挂接。其中 SAFETY_CONSTRAINT 直接影响⑧发布流程（未达标拦截），是业务影响最大的一条。
6. **来源图谱升级 → 全景感知是 mock 的**：`PROFILE.changes` 是写死的变更数组；真实实现需要来源版本 manifest diff 驱动（规划「每段用阶段版本号串起来：标准 v2 → 图谱 v2 → 任务 v1.3」幂等可重入）。

## 四、「全部数据入图」落地建议（分三批）

| 批次 | 内容 | 解锁 | 风险 |
|---|---|---|---|
| **第一批 · 补全供给侧** | 赛项评分点、证书考点结构化入图（`MAPS_TO` 映射 + 版本）；岗位能力图谱完成「能力点入图」 | 备赛/考证/岗位三个场景子图从 ready:false → ready；全景「全部」视图出现赛/证完整层 | 数据需人工映射审核，工作量最大；建议从导游专业 1+X 证书 + 2026 导游服务赛项试点 |
| **第二批 · 教学侧入图（展示层优先）** | 备课资源真实挂载（skillIds→能力项回挂）；任务考查关系展示层叠加（不建任务节点） | 子图「找资源」用真实数据；课程图谱子图能看到"这门课的资源挂在哪" | 不动版本机制（资源不随版本，R2 不变） |
| **第三批 · 回流层** | 掌握度当前值快照上节点（HAS_MASTERY，只读）；覆盖缺口 GAPS_ON 回流展示 | 学生/老师看图谱时带掌握度颜色；缺口驱动补资源、补训可视化 | 严格保持 PG 为准、异步同步；图谱上只读展示，杜绝任何掌握度写操作 |

**不建议入图**（规划明确）：排课、成绩明细、评价日志、审核日志——全部留在事务侧；图上只放结构与当前值快照。

## 五、遗留决策点

1. kmap.html 是构建生成文件但被 git 跟踪（graph/kmap-data.js 已 ignore）——需决定 ignore 还是重建提交。
2. 第 2 批梳理发现的「知识点编辑入口缺失」（PRD 5.5 要求新增/编辑/停用）——入图前补齐，否则知识点修订只能走构建链。
3. 场景子图模板的开放条件目前是硬编码 `ready:false`；「全部入图」后应改为按「该来源已发布版本是否存在」自动判断。
