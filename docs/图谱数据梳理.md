# 图谱数据梳理

> 2026-11-12 · 口径：演示原型（industry-analyzer-demo）。回答三个问题：**目前哪些信息入图了、后续信息怎么入图、图谱如何使用**。

## 一、图谱体系总览

平台里的"图谱"分三层，全景图谱是三者的合并视图：

| 层 | 名称 | 层级结构 | 当前数据来源 |
|---|---|---|---|
| 1 | 行业能力图谱（标准图谱） | 行业 → 子行业 → 岗位 → 能力项 → 技能 → 知识点/操作步骤/标准/案例 | Python 构建链（见 §2.1） |
| 2 | 专业知识体系（课程图谱） | 专业 › 课程分类 › 课程 › 任务 › 技能规范 › 知识点 | 平台导出 Excel + 能力↔技能映射 JSON |
| 3 | 全景图谱 | 以上两层 + 标准库（赛项、证书）+ 老师个人补充/贡献 | 运行时由前端合并 KMAP_DATA + 个人数据 |

## 二、目前哪些信息入图了

### 2.1 构建期入库（Python 链，改数据要重建）

```
raw-data/data_kmap-旅游行业19岗位-备份.py   ← 图谱骨架（唯一原始文件）
        │  data_kmap.py（引用 + 新兴标记 + 节点详情）
        ▼
build_kmap.py ──读──> raw-data/knowledge_system_*.xlsx（导游专业知识体系导出）
        │           docs/能力测评/导游专业-映射草稿.json（能力↔技能映射）
        │           口径统一在 data_assess.py（KNOWLEDGE_FILES / MAPPING_FILES / 计入规则）

graph/kmap-data.js（window.KMAP_DATA，全景图谱共用，构建生成勿手改）
```

## 三、后续信息怎么入图（入库路径）

| # | 入图内容 | 当前路径（原型） | 正式环境 |
|---|---|---|---|
| 1 | 行业/岗位/能力项骨架 | 手工整理 `raw-data/19岗位备份.py` → 重跑 `build_kmap.py` | 「能力图谱」模块 AI 生成 + 版本管理 |
| 2 | 专业知识体系 | 平台导出 Excel 放 `raw-data/`，在 `data_assess.KNOWLEDGE_FILES` 注册专业 id → 重建 | 「知识体系」模块生成（AI 接 Dify 工作流） |
| 3 | 能力↔技能映射 | AI 推导生成草稿 JSON（规则见 `.claude/skills/ability-skill-mapping/SKILL.md`）→ 映射审核页人工审核 → 已审核后重建生效 | 「图谱中心」映射任务流程（新建任务→AI 映射→审核→发布） |
| 4 | 老师个人贡献（增量反哺） | 能力地图添加个人节点 →「提交到标准图谱」→ 图谱中心「图谱建议审核」采纳（可改名）/退回 → 发布 → `GSuggest.published()` 并入标准图谱，全校可见，标「贡献·提交人」 | 同流程，落库 |
| 5 | 细化知识点 | 老师在知识体系知识点下细化（AI 辅助）→ 课程负责人审核共享 → 随全景版本发布 | 同流程 |
| 6 | 全景版本管理 | 排课/知识体系来源更新 → 同步更新进草稿 → 确认发布；已发布版本只读可回滚 | 平台版本服务 |
| 7 | 实训条件（非图谱本体，同链） | AI 推导草稿（`.claude/skills/training-condition-derivation`）→ 审核 → `build_assess.py` | 实训资源模块 |

**要点**：静态层（1–3）走"改文件→重建"，审核状态是计入闸门；动态层（4–5）走"前端提交→人工审核→发布"，不需要重建。

## 四、图谱如何使用（消费方）

1. **能力地图**（`kmap.html`，教师端/管理端）：浏览/搜索图谱、AI 自检（规则来自 kmap-ai-selfcheck SKILL.md，构建时注入）、AI 细分、技能缺口检测；**「带入备课」**——把技能/知识点链路写入 `kmapToWorkbench`，跳转备课工作台（workbench.html 读取生成备课范围建议）。课次「去备课」也走同一条通道（补训/辅导课次带着针对的技能）。
2. **全景图谱**（`graph/knowledge-graph-view.html`）：三来源合并视图（来源标"能力图谱/知识体系/赛项/证书/自建"）、搜索定位、筛选、渐进展示（默认 3 层）、保存子图、版本对比。
3. **能力测评 / 专业建设测评**（`assess.html`）：技能覆盖率、岗位能力达成评估——与图谱共用同一份数据与口径（§2.1）。
4. **教学闭环**：图谱技能 → 备课资源关联课次自动带技能（`fillSkillsFromRes`）→ 发布任务时确认考查技能/知识点 → 学生提交 → 老师评价 → **技能达成（最近一次通过）/知识点掌握（最近一次老师确认评价）回流统计** → 学情页面展示，缺口可发起补训/辅导（补训课次再从图谱带技能）。

## 五、本次梳理发现的问题

1. **`kmap.html` 是生成文件但被 git 跟踪**（`graph/kmap-data.js` 已 ignore，`kmap.html` 没有）——本次重建后 kmap.html 出现未提交差异（模板里"图谱建议审核"改名同步进来了）。建议二选一：把 kmap.html 也加进 .gitignore（部署时构建），或接受"每次模板改动需同步重建 kmap.html 再提交"。
2. **数据双入口风险**：`build_kmap.py` 与 `build_assess.py` 各自读同一批原始文件，口径靠 data_assess.py 统一——目前一致（三端一致性检查 83% 已验证），但新增专业时要记得两边同时注册。
3. **运行时 SEED 与构建数据耦合**：全景图谱映射任务的种子（kg_tasks_v7）是前端写死的，行业名/图谱名与 KMAP_DATA 无强校验，改名时容易两处不同步（本次"岗位图谱"改名风波的根源）。
